# Проект 1. Перезапись памяти: накопление против точной правки

**Сложность:** базовая. Тема **CPU-first**: полный протокол на процессоре
разрешён, но обязан начинать вывод с предупреждения: все величины времени и
пропускной способности с процессора несравнимы с картой, и в отчёт их ставить
нельзя.

---

## Легенда

Диспетчерская службы такси хранит текущее положение машин на одной электронной
доске фиксированного размера. Каждый позывной кодируется своим шаблоном на этой
доске, а координаты машины записываются вдоль этого шаблона. Шаблоны разных
позывных могут частично перекрываться - доска не бесконечная, а машин много.

Диспетчер А при каждом сообщении просто добавляет новую запись. Старые
координаты того же автомобиля остаются в памяти вместе с новыми, поэтому при
чтении смешиваются и история этого автомобиля, и помехи от других позывных.

Диспетчер Б перед записью смотрит, что память сейчас возвращает по нужному
позывному, вычитает этот вклад и записывает новое значение. Для отдельного
позывного это похоже на «стереть и записать». Но шаблоны перекрываются, и
правка одного автомобиля слегка задевает чтение остальных.

У обоих доска содержит одинаковое число чисел. Вопрос проекта - как расходятся
эти два правила при росте числа перезаписей и при росте интерференции между
записями.

---

## Гипотеза

При одинаковом размере состояния delta rule сохраняет более высокую retrieval
accuracy, чем additive memory, когда одни и те же или близкие ключи
многократно получают новые значения; преимущество увеличивается с числом
перезаписей и уровнем интерференции.

Гипотеза может подтвердиться, опровергнуться или дать смешанный результат -
при корректном протоколе все три исхода оцениваются одинаково.

## Baseline и кандидат

| | Baseline | Кандидат |
|---|---|---|
| правило | `S ← S + v kᵀ` | `S ← S + (v − S k) kᵀ` |
| смысл | дописать | стереть по ключу, затем записать |
| состояние | `S` размера `d_v × d_k` | ровно того же размера |
| обучаемых параметров | нет | нет |

Выравниваются: `d_k`, `d_v`, начальное состояние, наборы ключей, значений и
запросов, порядок записей. **Число скаляров в состоянии обязано совпадать
точно** - это проверяется программно, а не на словах.

Сравнение выровнено по размеру состояния, но **не по стоимости одного
обновления**: delta rule дополнительно читает `S k`. Поэтому вывод проекта
относится к качеству памяти при одинаковом размере состояния, а не к качеству
при одинаковом числе операций или одинаковой задержке.

Ключи нормируются к единице: для delta update с шагом 1 это обеспечивает
точную замену чтения вдоль текущего ключа сразу после записи.

## Данные

Генератор синтетический, никаких внешних датасетов.

- `n_keys` ключей единичной длины в `R^{d_k}`;
- каждый ключ получает `writes_per_key` значений в случайном порядке по потоку;
- значения берутся из кодбука на `codebook` векторов и **не повторяются внутри
  истории одного ключа** (`replace_values = False`): повтор дал бы additive
  шанс угадать актуальное значение не из-за свежести, а из-за случайного
  совпадения;
- правильный ответ на запрос к ключу - **последнее** записанное по нему значение.

**Геометрия своя у каждого примера оценки.** Ключи и кодбук разыгрываются не
один раз на весь набор, а отдельно для каждого потока. Если разыграть их один
раз, бутстрэп окажется условным на одной конкретной выпавшей геометрии, и
неопределённость от того, какая геометрия досталась, в интервал не войдёт
вовсе. А в гипотезе про независимые ключи это существенная часть порождающего
процесса. Три seed эту дыру не закрывают: seed - уровень репликации, а не
единица бутстрэпа.

Два **разных** параметра интерференции, смешивать их нельзя:

1. **Загрузка памяти** `load = n_keys / d_k`, сетка по ней - `loads`. Ключи
   независимые изотропные при любом `n_keys` (`key_mode = iid`) - одна и та же
   семья на всей сетке. Это та самая ёмкость из
   занятия 2: число координат ключа ограничивает, сколько произвольных пар
   помещается без взаимного шума.
2. **Попарная близость ключей** `rho` при фиксированном `load ≤ 1`, сетка по
   ней - `rhos`. Матрица Грама задаётся точно: `k_i · k_j = rho` для `i ≠ j`. Здесь меняется только
   геометрия, а количество записей остаётся прежним.

Третий параметр - **число перезаписей** `writes_per_key`, сетка по нему -
`writes`. Число независимых потоков в батче задаёт `batch`.

## Метрики

**Основная:** доля правильно восстановленных актуальных значений по запросам к
активным ключам. Декодер косинусный, по всему кодбуку; уровень случайного
угадывания равен `1 / codebook`.

**Дополнительно:** норма состояния `‖S‖_F`, кривые по всем трём параметрам.

Единица парного бутстрэпа - **поток**, то есть один пример оценки. Ни запросы
внутри потока, ни три финальных seed единицами бутстрэпа не являются.

## Правило финального вывода

Три финальных seed недостаточны для классического теста значимости.
Формулировка «статистически значимо» по трём seed запрещена.

Преимущество delta rule считается установленным только при одновременном
выполнении трёх условий:

1. разница `accuracy_delta − accuracy_additive` положительна на каждом из seed
   `17`, `23`, `42`;
2. средняя парная разница превышает заранее зафиксированный порог `δ`
   (по умолчанию 0,02 абсолютной accuracy);
3. минимум для двух из трёх seed парный бутстрэп-интервал разницы по примерам
   оценки целиком лежит по одну сторону от нуля.

Если хотя бы одно условие не выполнено, вывод формулируется так: «устойчивого
преимущества при данном бюджете не обнаружено».

## Обязательный минимум

- независимый FP64 reference **отдельным путём кода**, не вызывающим основную
  реализацию;
- обе схемы реализованы и сверены с reference до первого содержательного вывода;
- сетка по загрузке памяти, сетка по числу перезаписей и сетка по близости
  ключей - не менее пяти точек в каждой;
- **негативный контроль:** одна запись на ключ и ортогональные ключи. Команда
  формулирует ожидаемый результат из формул обновления **до** запуска и
  проверяет его. Провал означает ошибку реализации, а не открытие;
- три финальных paired seed `17`, `23`, `42` на главной точке;
- **главная точка выбирается на отдельном пилотном seed, не входящем в
  финальную тройку**, и фиксируется в `EXPERIMENT.md` до финальных прогонов.

Критерий информативности главной точки, фиксируется до финальных прогонов:
**лучшая из двух схем** должна попасть в интервал
`случайное угадывание + 0,02 < accuracy < 0,98`.

**В полосе обязан лежать максимум по обеим схемам**, и по нему же идёт
ранжирование внутри полосы. От перестановки имён схем ответ не меняется, и это
закреплено тестом.

**Выбирать точку ни по разнице между схемами, ни по уровню одной названной
схемы нельзя.** В первом случае главная точка подбирается под тот самый эффект,
который потом объявляется результатом. Во втором режим калибруется под
участника, и вывод перестаёт относиться к задаче.

**Низкий baseline на выбранной точке - не повод её отбрасывать.** У потолка
baseline точку убивает: улучшать нечего, преимущество не проявится при любом
механизме. У пола - наоборот, даёт сильнейшую форму результата «кандидат решает
то, чего baseline не решает вовсе». Самая содержательная точка лестницы - та,
где кандидат не у пола и не у потолка.

### Широта, обязательная для зачёта темы

Эти пять требований одинаковы во всех темах курса и проверяются до содержания.

- **режимная сетка не менее пяти точек** по главному параметру темы - КРОМЕ
  тем, где формальная постановка или устройство задачи явно фиксируют иную
  конечную сетку; там приоритет у минимума самой темы, и добавлять точки ради
  числа пять не надо. Сколько точек обязательно в вашей теме, сказано в
  «Обязательном минимуме» выше. Требование пяти точек стоит против сеток,
  подогнанных под удобную картинку, а не против конечных сеток, заданных
  условием задачи.

  В сетке обязана быть заранее зарегистрированная **теоретическая нулевая
  точка** - режим, в котором механизм гипотезы предсказывает нулевой эффект, и
  это предсказание выводится из устройства механизма **до** запуска. Режим, где
  механизм предсказывает лишь «эффект меньше, чем на главной точке», нулевой
  точкой НЕ является: это диагностика затухания, и называть её нулевой точкой
  нельзя.

  Формулировка важна. Требовать «в сетке обязан найтись режим, где эффект
  исчезает» нельзя: это толкает двигать сетку после просмотра результатов, пока
  нужная картинка не появится. Требуется другое - назвать до прогона точку, где
  эффекта быть не должно, и проверить. Если эффект там не исчез, это
  полноценный результат, который надо объяснить, а не повод менять сетку;
- **независимый FP64-оракул пишет не автор реализации.** Человек, писавший
  механизм, повторит в оракуле собственную ошибку - перепутанную ориентацию
  внешнего произведения, потерянный множитель, знак, - и оракул подтвердит её. Кто что писал, указывается в `EXPERIMENT.md`;
- **механистическая диагностика обязательна.** Недостаточно показать, что
  кандидат выигрывает. Нужно заранее назвать величину, которая обязана
  измениться, если работает именно заявленный механизм, измерить её и показать,
  что она изменилась. Если кандидат выигрывает, а эта величина не двигается,
  объяснение придётся искать другое - и это полноценный результат;
- **разбор пола и потолка обязателен.** При нулевом или отрицательном
  результате показывается, что дело не в сломанном baseline, не в потолке, не в
  поле и не в нехватке примеров оценки. Агрегатная метрика на нуле не различает
  «модель учится, но не дошла» и «модель не учится вовсе»: рядом приводится
  величина, чувствительная к обучению, и сравнивается с уровнем случайного
  угадывания, а потери - с теоретическим минимумом задачи, а не с нулём;
- **размер набора оценки считается расчётом мощности до пилота** и после
  просмотра интервалов не увеличивается. Нужна оценка, при которой стандартная
  ошибка разности заметно меньше порога δ. «Взяли 512, потому что быстро» -
  не обоснование.

## Как делить работу на команду

Тема рассчитана на 3-4 человека и делится не по строкам кода, а по
ответственности:

- **данные** - генератор, детерминированные проверяющие, негативные контроли;
- **механизм** - baseline и кандидат, выравнивание бюджетов, тесты инвариантов;
- **корректность** - независимый FP64-оракул, написанный **не** автором
  механизма, и механистическая диагностика;
- **протокол** - `EXPERIMENT.md`, пилот, три seed, бутстрэп, сборка всех чисел
  и графиков из сырых результатов.

Роли фиксируются в `EXPERIMENT.md`. Пересечение допустимо, но оракул и механизм
пишут разные люди - иначе проверка теряет смысл.

## Бюджет вычислений

Отладка, генератор и проверки корректности идут на процессоре. Обязательный
полный протокол практически выполним только на карте: состояние размером
256x256 на **4096 независимых потоках** на процессоре считается неприемлемо
долго. Формально процессор не запрещён - см. ниже, - но обязательная
конфигурация рассчитана на карту.

Потоков именно 4096, а не тысяча: на тысяче карта простаивает большую часть
прогона. Память при этом держится с запасом - состояние 4096x256x256 плюс
своя геометрия ключей на каждый пример дают порядка 4 ГиБ на V100 16 ГБ.

Корректность устанавливается по FP32 и независимому FP64 reference; FP16
оракулом корректности не является. В этой теме обучения нет вовсе, поэтому
сверка возможна практически до машинной точности - и выполнять её надо
перед любым содержательным числом, а не печатать рядом с результатом.

**Полный протокол разрешён и на процессоре**, но обязан печатать
предупреждение: величины времени с процессора несравнимы с картой, и в отчёт
такие числа не идут. Режим `--mode smoke` остаётся процессорным - он для того
и нужен, чтобы отладить весь путь до первого запуска на карте.

Порядок работы такой: пилот, заморозка постановки, финальные три seed.
Сколько идёт ваш полный протокол, вы узнаете на пилоте - и планируете от этого
числа. Прогон, который тянется заметно дольше, - это почти всегда дефект
постановки, и досчитывать его бессмысленно.

Планировать сетки шире заданных не надо: семь-восемь точек по параметру
удорожают полный протокол кратно. Пять точек по параметру - это требование
регламента, и его достаточно.

## Опорная конфигурация

Это рабочая конфигурация: на ней эксперимент доходит до вердикта.
От неё и стройте.

**Это ОРИЕНТИР, а не предписание - но не всё в нём одинаково свободно.**
Разница принципиальная, и спутать её дорого:

- **Протокол менять нельзя.** Порог практической значимости, главная
  точка, финальные seed, нулевая точка и допуски контролей заданы
  постановкой темы и объявляются ДО прогонов. Изменив их, вы получите
  другой эксперимент, а не лучший результат в том же: подвинуть порог
  после просмотра чисел - это подгонка, и работа не засчитывается.
  Если считаете, что порог выбран неверно, это обсуждается до заморозки
  и записывается в `EXPERIMENT.md` с обоснованием.
- **Модель и обучение - ваша территория.** Размер, ширина, число шагов,
  батч, скорость обучения: ищите лучше, это и есть работа. Опорные
  значения говорят лишь, что на них результат получается.
- **Задача - смешанный случай.** Часть её параметров определяет, ЧТО
  измеряется, и задана постановкой; часть - лишь насколько трудно, и
  свободна. Что именно закреплено в вашей теме, сказано в разделе
  «Обязательный минимум» выше; при сомнении считайте параметр
  закреплённым и спросите.

И общее правило поверх всего: менять - только ПОСЛЕ того, как
воспроизвели опорный режим. Иначе непонятно, с чем сравнивать, и
отличить «обошёл» от «сломал» будет нечем.

**Проверка режима.** На этих настройках baseline даёт вот что
(финальные seed `17`, `23`, `42`):

### Тупики

Конфигурации ниже результата не дают. Время на них не тратьте.

- **генерация данных питоновским циклом по примерам** - QR-разложение 64x64 на
  каждый из 4096 примеров оценки по отдельности: карта простаивает, и полный
  протокол выходит за потолок. Геометрия разыгрывается пакетными операциями по
  всему батчу сразу.

Это НЕ запрет: если у вас есть основание думать, что тупик обойдён,
проверяйте. Но сначала воспроизведите опорную конфигурацию, иначе
отличить «обошёл» от «сломал» будет нечем.

## Что может пойти не так

- **Ненормированные ключи** делают delta update неустойчивым. Ловится коротким
  FP64-тестом, а не глазами по графику.
- **Слишком слабая или слишком сильная интерференция.** В одном режиме влияние
  геометрии ключей может быть практически незаметно, в другом обе схемы теряют
  полезный сигнал. Пилот должен найти информативную область между этими
  случаями.
- **Структурное падение baseline.** Низкую accuracy additive нельзя
  автоматически объявлять floor или «плохим baseline». Нужно из правила
  обновления объяснить, какую информацию о порядке записей память вообще
  способна сохранить, и отделить этот эффект от интерференции между ключами.
- **Ошибка ориентации состояния** (перепутаны `d_k` и `d_v`) обнаруживается
  только независимым reference. Вторая реализация, вызывающая тот же основной
  код, подтвердит любую одинаковую ошибку.
- **Смешивание двух параметров интерференции.** Если менять `n_keys` и ждать,
  что это «просто интерференция», в одном sweep поедут сразу загрузка памяти,
  число ключей и длина потока.
- **Выбор главной точки по финальному seed.** Это утечка отбора: точка выбрана
  по тем же данным, на которых потом объявляется результат.

## Что нужно для высшего балла

Сообщить победителя в главной точке недостаточно. Нужна сетка взаимодействия
«число перезаписей x загрузка памяти» на пилотном seed, и в ней - заранее
названная нулевая точка. Здесь она выводится из формул: при одной записи на
ключ и ортогональных ключах обе схемы обязаны дать одно и то же, потому что
стирать нечего. Это предсказание проверяется, а не подбирается.

Отдельно разведите два источника проигрыша аддитивной схемы, иначе вывод
получится неверным. Сумма коммутативна, поэтому при нескольких записях на ключ
аддитивная схема **структурно** не хранит порядок значений - это не
интерференция, а другое явление. Нужны три режима: только перезапись
(ортогональные ключи, несколько записей), только интерференция (одна запись на
ключ, высокая загрузка) и оба сразу.

Отдельно ценится честное разделение двух источников интерференции: совокупной
загрузки памяти и попарной близости ключей. Это принципиально разные вещи, и
формальная гипотеза говорит в том числе про близкие ключи.
